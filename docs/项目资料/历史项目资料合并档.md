# 原文：项目完整总结（2026-08-19）

词境（Wordscape）项目完整总结
最后整理：2026-08-19（北京时间）

一、项目定位与目标

项目名称：词境（Wordscape）
项目目录：E:\Study\English-Codex\词境
线上网址：https://wordscape.weleuther900.workers.dev/

这是一个以英语单词学习、语境例句、间隔复习和多设备同步为核心的网页/PWA 项目。用户使用 Windows、iPhone 和 iPad 三端学习；Windows 通过桌面一键图标打开线上网址，iPhone/iPad 可以使用 Safari 访问并添加到主屏幕。

本项目的核心要求不是“只展示单词”，而是：
1. 学习、复习和单词本的数据能在 Windows、iPhone、iPad 之间同步。
2. 已学习单词与未学习单词在学习页面、复习页面中的出现规则必须符合每日计划逻辑。
3. 复习不能让人有持续刷任务、被任务追赶的感觉。
4. iPhone/iPad 即使作为 PWA/离线网页，也要尽可能正确更新静态资源并保存本机数据。
5. 不泄露同步密钥；云端只保存加密内容。


二、当前技术架构

1. 前端与本地运行

主要前端目录：public\
主要应用逻辑：public\app.js
同步加密/合并逻辑：public\sync-core.js
离线服务工作线程：public\service-worker.js
PWA 配置：public\manifest.webmanifest
离线刷新页：public\refresh.html
每日中英文谚语：public\daily-quotes.js

桌面本地开发服务：server.js
本地状态文件（Windows 本地运行时）：data\state.json
本地启动命令：npm run start

Windows 本地运行使用 Node.js；iPhone/iPad 与线上 Windows 使用浏览器的 IndexedDB/localStorage 设备存储。线上部署不依赖 Windows 本地服务。

2. Cloudflare 云端

Cloudflare Worker 源码：cloudflare\worker.js
Cloudflare 配置：cloudflare\wrangler.toml
数据库：Cloudflare D1，绑定名 WORDSCAPE_DB，实际数据库名 wordscape-sync。
Worker 名称：wordscape。
线上 API：/api/sync

云端同步内容经过 AES-GCM 加密。同步密钥只保存在各设备本机，不能、也不应被写入云端、日志或本文档。

云端使用“版本号 + 冲突保护”的方式保存数据：
- sync_profiles：保存同步档案版本、元数据和分片信息。
- sync_chunks：保存较大的加密密文分片。
- 大档案拆分后写入 D1，避免单个数据库字段过大。
- 写入时检查 revision，多个设备同时修改时不会静默覆盖。
- 学习记录全量重置使用 learningResetAt 标记，旧设备不能把已清除的记录重新写回云端。

3. iPhone/iPad 离线包

生成命令：npm run ios:web:prepare
生成目录：ios-web\
生成的历史压缩包：词境-iOS-v7.zip 至 词境-iOS-v17.zip（当前目录中保留多个历史版本）。

ios-web 是 Cloudflare 部署的静态资源来源。它包含网页、PWA 资源、离线词典/例句相关资源和服务工作线程。每次改动前端后，需要重新生成该目录并部署，iPhone/iPad 才能获得同一版本。


三、项目主要文件与作用

1. public\app.js

负责页面路由、学习页、复习页、词表、设置、单词导入、学习状态、复习排程、云端同步触发、PWA 页面上的同步状态显示等。

2. public\sync-core.js

负责：
- 加密前的状态压缩/整理。
- AES-GCM 加密与解密。
- gzip 压缩（浏览器支持时）。
- 多设备状态合并。
- 词本、单词、批次、学习上下文、复习日志、设置、重置标记的合并。
- 不把同步密钥包含进可同步状态。
- 复用本次网页会话中的 PBKDF2 派生密钥，减少 iPhone 上重复加密的等待。

3. cloudflare\worker.js

负责：
- 静态网页资源分发。
- /api/sync 的 pull、sync、delete 请求。
- CORS 白名单（线上域名和本地 localhost/127.0.0.1）。
- 加密内容分片读写。
- 同步 revision 冲突处理。
- 重置标记保护。
- 新版轻量“current”确认响应；只有明确声明支持 lightweight 的新版页面会收到该响应，旧页面仍收到兼容的 found + payload 响应。

4. public\service-worker.js

负责 PWA 离线缓存。首页导航采取优先获取线上最新版、失败才用缓存的策略。静态资源通过版本号和缓存名称递增来促使 iPhone/iPad 更新。

5. launch.vbs / start.cmd / 创建桌面图标.ps1

负责 Windows 桌面启动。当前目标是直接打开线上网址，而不是启动本地 4173/4174 服务。

处理结果：

五、学习页面规则：用户反复确认过的最终业务逻辑

1. 每日新学数量

每日新学数量由“设置 -> 每日新学”决定。用户用“每天计划学习 200 个词”作为主要示例；程序按设置值运行，代码默认值仍可在设置中修改。

2. 当天已经学习的单词

当天学习计划中的单词，只要已经学习过，当天仍然可以在“学习”页面看到，以便继续浏览和完成当日学习。

3. 次日的已学词处理

如果一个单词在前一天已经学习过：
- 从第二天起，不再显示在“学习”页面。
- 会根据复习规则进入“复习”页面。

4. 次日的未学词处理（最重要的要求）

用户明确要求：当天没有手动完成初学的词，次日仍需留在学习页面。

以每日计划 200 词为例：
- 第一天计划 200 个词。
- 当天已学习 150 个。
- 次日：这 150 个词不再出现在学习页面，转入复习体系；前一天尚未学习的 50 个词必须继续留在学习页面。
- 次日学习页面总数仍保持为 200：先放入这 50 个遗留未学词，再补充 150 个新的词。
- 之后每天按同一规则滚动。

已实现的核心逻辑：dailyStudyWordsForBatch()。
逻辑包括：
- 先把过去日期中已经 learningSeen 的词转为可复习状态。
- 保留旧计划中未 learningSeen 的词作为 carry-over。
- 用新词补足每日目标数量。
- 已经学过的词不再被重新当作“新学词”。

5. 学习页批次标签

用户不希望在学习页看到“第 1 批 · 5485 词”“第 2 批 · 5485 词”等批次切换按钮。

处理：已从学习页面渲染中移除顶部 batch-select 批次按钮。批次数据仍保留在后台，用于词本与计划逻辑；只是用户界面不再显示这些标签。


六、复习规则与“不要像做任务”的要求

用户反馈：不希望学了很久、复习很久后仍有强烈“完成任务”的感觉。

处理方向：
- 学习和复习界面文案改为更接近“慢慢重温”，不把复习描述成硬性任务闸门。
- 取消/弱化硬性复习门槛感。
- 新学词完成后，只有少量（最多 8 个）可以在同一天做轻度巩固；其余进入约 18 小时后的下一次复习，避免同一天反复刷同一批词。
- 复习采用间隔复习字段，例如 dueAt、stability、difficulty、reviewCount、lapses、lastReviewAt。
- 复习记录会保存回答正确性、反应时间、上下文、下次时间等数据。

注意：复习不是无限堆积的“每日任务清单”。每日复习目标只是节奏提示，用户可以分散完成。


七、学习记录清空：用户明确要求过的操作与保护

用户要求：“删除现在里面的所有学习记录”。

已执行/已实现的内容：
- 所有单词的学习进度、学习日期、复习日期、复习次数、稳定度、难度、上下文记录、复习日志等可以全局清空。
- 单词本、单词内容、例句、设置保留。
- resetAllLearningProgress() 及 scripts\reset-learning-progress.js 用于实现/验证该操作。
- 清空时写入 learningResetAt。
- 该时间戳会同步到 D1，防止旧设备离线后再次连接时，把旧学习记录重新合并回来。
- 曾在该轮处理中通过 --confirm 执行本地记录重置，并将清空状态同步到云端；当时验证结果为日志 0、已学习 0、待复习 0，所有单词回到 learning 状态。

后续规则变化：
- 曾一度设为“清空后立即自动同步”。
- 后来用户要求只手动同步时改为等待手动。
- 最新要求又变为“每 4 小时自动完整同步一次”，所以现在清空后的更改会在下次自动同步时上传，也可以点击“立即同步”马上上传。


八、三端同步：需求、实现与历史问题

1. 用户的同步要求

用户反复强调：Windows、iPhone、iPad 必须及时同步；同步的不只是学习记录，而是“所有内容”，包括：
- 词本和词本状态。
- 单词本身以及自定义内容。
- 学习状态。
- 每个词的例句与上下文。
- 所有复习记录。
- 导入记录。
- 设置。
- 全局学习记录清空标记。

2. 同步安全

- 同步密钥由用户在三台设备输入同一把密钥。
- 密钥只保存在设备内。
- 云端保存的是加密密文，不保存明文词本、单词或密钥。
- 丢失同步密钥后，不能从云端找回。

3. 初始全量同步与日常同步

用户词库规模很大。一次本地状态的 JSON 曾测得约 14.5 MB，包含约 10,973 个单词。因此：
- 新设备第一次连接或设备版本明显落后时，必须下载/合并完整加密档案，耗时比普通操作长。
- 日常状态确认不应每次都下载完整档案。

4. 同步速度优化

发现的问题：原实现每次检查云端，即使版本完全一致，也会读取 D1 所有分片并下载完整密文；这导致 Windows 和 iPhone 都感觉同步慢。

已做的优化：
- Worker 支持轻量 current 响应：设备 revision 与云端一致时，只返回很小的版本确认信息，不下载完整加密档案。
- 新页面通过 lightweight: true 显式声明支持该响应。
- 为旧版缓存页面保留兼容：没有 lightweight 标志的旧页面仍得到原先 found + payload 响应，避免“云端返回了未知同步状态”。
- sync-core.js 缓存当前会话的 PBKDF2 派生密钥，减少反复加/解密的计算开销。

5. “未知同步状态”问题

问题表现：设置页面出现“同步失败：云端返回了未知同步状态”。

原因：Worker 先上线了新的 current 状态，而某些已缓存的旧 app.js 不认识这个状态。

修复：
- Worker 仅对新版、明确携带 lightweight: true 的请求发送 current。
- 旧页面保持旧协议响应。
- 已增加 verify-cloud-worker.js 测试：同时验证旧客户端兼容响应和新客户端轻量响应。

6. “正在同步 / 已同步”反复跳转问题

问题表现：状态文案不断在“正在同步”和“已同步”之间切换。

原因：为了加快跨设备发现，曾把前台轮询缩短到 8 秒；但每次轻量检查也更新了 UI 状态，因此看起来像不断同步。

中间处理：曾改成纯手动同步，移除了定时检查、启动、联网、回到前台和学习记录变更时的自动请求。

最新用户要求：
- “已同步”需要带同步日期。
- 每 4 小时全部自动同步一次。

当前最终规则：
- 手动点击“立即同步”时，立即进行完整双向同步。
- 成功同步后，4 小时后自动发起下一次双向同步。
- 若页面/设备在后台，浏览器受到系统暂停时无法保证准确在后台时刻执行；iPhone/iPad 再次前台打开且已过 4 小时时，会补做同步。
- 网络重新可用、应用重新前台时，只有距离上次成功同步已满 4 小时，才自动同步。
- 单词学习、复习、设置改动不会立刻反复上传；状态会提示“本地改动待同步”，在下次自动同步上传，也可以手动点击立即同步。
- “已同步”使用北京时间完整日期和时间，例如：已同步 · 2026-08-15 22:30（北京时间）。

7. 关于“完整同步”的准确说明

每 4 小时的自动同步执行完整的双向同步流程：检查云端版本、下载别的设备变更、合并本地变更、必要时上传完整加密状态并处理冲突。

如果三端数据本来已相同，协议会只做轻量版本确认，而不会无意义地重新传输十几 MB 数据；这不影响数据完整性，反而避免浪费流量和等待时间。


九、iPhone/iPad 更新与缓存问题

用户曾反馈：iPhone/iPad 刷新没有用、看不到新改动。

原因与处理：
- PWA 的 service worker 可能缓存旧版 index.html、app.js 和 CSS。
- 仅改源码、不递增静态资源版本，移动端可能继续读旧缓存。
- 每次部署前端改动时，已递增 index.html 中 app.js/sync-core.js/service-worker.js 的版本查询参数。
- 每次部署前递增 service-worker.js 的 CACHE_NAME（例如 wordscape-shell-v29、v30……v37），使旧缓存淘汰。
- ios-web 每次重新生成，再由 Wrangler 上传到 Worker 静态资源。
- 提供 refresh.html 作为移动端刷新辅助页面。
- 设置页中提供“更新此设备”按钮；用户也可在联网状态下关闭并重新打开 PWA。

现实限制：iOS Safari/PWA 在后台时会被系统暂停，网页不能像原生 App 一样保证后台定时任务准点运行。因此“4 小时自动同步”在 iPhone/iPad 上以“前台运行或下次重新前台时补做”为准。

## 3. 历史：基础版共识与范围（截至 2026-08-04）

> 本文汇总截至 2026-08-04 的讨论结论，用于后续设计与开发对齐。本文不是最终技术规格，也不代表已经开始实现。

## 1. 项目定位

- 项目名称：**词境（WordScape）**。
- 核心目标：将用户自己的英语词表放入语境中学习，并通过可验证的、间隔式复习，尽可能将词汇长期记住。
- 目标使用者：英语入门阶段（A0–A1）的单人自用学习者。
- 产品重心：不是单纯阅读 AI 故事，而是“**语境学习 + 主动复习 + 自适应排程**”的记忆系统。
- 使用平台：第一版仅面向 **Windows 上的 Google Chrome**；手机支持留待后续版本。
- 原则：不做打卡、徽章、排行榜等游戏化机制；学习与复习本身是核心。

## 2. 学习目标与负荷规则

### 2.1 每日 200 词

- “每天 200 词”是学习目标，而非只浏览一遍的展示指标。
- 词语出现在故事中，不等同于已经掌握；每个词都必须进入可追踪的复习流程。
- 系统需要明确区分：待学、正在学习、待复习/逾期、已掌握等状态。

### 2.2 复习优先门槛

- 当到期或逾期的复习词达到 **100 个**时，暂停把新词纳入正式学习。
- 暂停期间，词表可保留、可预览，但不应被错误计作已学习或已掌握。
- 历史到期词不能被隐藏或丢弃；应先完成复习再恢复正式新词学习。

## 3. 首次学习

1. 用户导入词表后，AI 按已选择的词和义项生成适合入门水平的英语故事或短语境。
2. 学习者通过语境认识单词的当前义项；中文释义用于理解，默认应避免直接暴露，以保留“先猜后看”的过程。
3. 每个目标词可查看其当前义项、音标和例句。
4. 第一次学习完成后，应有一次“当日巩固”，但不应把大量同日反复当作长期记忆的替代品。

## 4. 复习设计（已确认）

### 4.1 复习与首次学习不同

“先回忆、再显示候选、通过语境选词”**只用于复习**，不用于首次学习。

复习题的基本流程：

1. 先展示新的中文情景和一条英文挖空句；不展示目标词和候选答案。
2. 学习者先在脑中回忆应填的英文词。
3. 点击“显示候选”后，从 4 个候选英文词中选择答案。
4. 系统记录是否答对、是否使用提示，以及答题时间等复习数据，并据此安排下一次复习。

示例（目标义项：`bank = 银行`）：

> 爷爷用手机银行缴纳了水电费。
> Grandfather paid his utility bill with a ____ app.

候选：`bank` / `bridge` / `ticket` / `book`

### 4.2 每一次复习必须是新情景

- 同一“单词 + 义项”在每次复习中，中文情景和英文例句都必须不同。
- 新题不得复用此前的故事、中文情景、英文句子，或仅作表面改写。
- 新题要避开已使用的人物、地点、事件、动作和句式；但义项必须保持一致。
- 系统需要为每个“单词 + 义项”保存已用情景记录（如场景标记、句子和日期）。
- 生成新题时，向 AI 提供历史情景约束；本地还要做文本重复检查。

### 4.3 复习的评分方向

- 不采用“中文提示后键盘拼写英文单词”作为基础版的主要答题方式。
- 复习要有可验证的对错记录，不能只依靠“我记住了/没记住”的主观自评。
- 候选词应尽量是同词性、在语境中容易混淆的词，避免答案过于显而易见。
- 答错：记为遗忘，进入重新学习或更短的复习间隔。
- 答对：根据是否使用提示、答题表现等映射为不同的记忆质量记录。具体的评分映射将在实现前再细化。

## 5. 间隔复习模型

- 使用 **FSRS（Free Spaced Repetition Scheduler）** 作为排程核心，不再使用固定的 `1 / 3 / 7 / 14 ...` 天间隔表。
- 排程最小单位为“**单词 + 义项**”，而不是笼统的单词；不同义项分别拥有复习历史与记忆状态。
- 初始目标记忆率暂定为 **92%**，后续应根据实际复习负荷和真实正确率调整。
- 不能将目标记忆率设为 100%；接近 100% 会让复习量急剧上升。
- 初期使用 FSRS 默认/初始参数；积累数百条有效复习记录后，再在本地按用户自己的历史优化参数。优化无需频繁进行，按月即可。

## 6. 美式发音与朗读（已确认）

- 发音用于帮助学习与复习，**不是**测评或答题评分功能。
- 每一个目标单词必须有独立的播放按钮。
- 每一个英文句子必须有独立的播放按钮。
- 默认以美式英语（`en-US`）声音为主。
- Google Chrome 中应提供语音选择与试听；若设备没有可用的美式英语声音，应明确提示配置，不应静默改用英式声音。
- 单词和句子的播放速度应可调；单词默认宜比句子更慢。

## 7. 数据与技术原则

- 单人、本地优先：词表、学习状态、复习历史、已用情景和设置应保存在本机浏览器中。
- 建议以 IndexedDB 保存主体学习数据，localStorage 仅保存轻量设置；后续提供 JSON 备份与导入恢复。
- 原项目书中的 AI 方案为 DeepSeek。当前实现前需要确认模型、浏览器直连可行性与错误重试策略；如果使用用户 API Key，必须明确告知 Key 和待生成的词表内容会直接发送给 AI 服务商。
- AI 的结构化输出需要本地校验、失败重试和可人工修正，不能只因返回了 JSON 就视为正确。

## 8. 建议先实现的基础版本（待确认后开始）

## 11. 展示风格、艺术性与交互原则（已确认）

### 11.1 总体方向

- 视觉参考：借鉴 Apple 官网的克制感、清晰信息层级、充足留白和细腻的动态反馈；不复制其产品发布页，也不做营销网站。
- 整体气质：**安静的高级感 + 有温度的阅读空间 + 精确而自然的交互**。
- 产品应像“一本设计精良、会回应学习者的书”，而不是密集数据后台、传统卡片堆或游戏界面。
- 艺术性服务于专注与记忆线索，不能抢走英语文本和复习题本身的注意力。

### 11.2 页面与信息层级

- 顶部采用极简、半透明的悬浮导航：`词表 / 学习 / 复习 / 设置`；页面滚动时可轻微收缩，但不使用复杂侧栏。
- 首页第一屏只表达一个主要任务，例如“今天，重新遇见 24 个词”，并提供单一主操作“开始复习”。
- 不在首页堆叠密集仪表盘、夸张进度条、连续天数或分数。
- 阅读页以宽留白和清晰的英文排版为主；中文是辅助信息，通过轻量展开查看，而不是与英文内容争夺视觉焦点。
- 复习页一屏只完成一道题：中文新情景、英文挖空句、延迟显示候选、答题后进入下一题。

### 11.3 词、句与复习的交互

- 点击单词时，在原文附近平滑浮出信息卡，显示音标、当前义项和美式发音；关闭后立刻回到原来的阅读位置，不跳转页面。
- 每个英文句子都可独立朗读。播放时只对当前句做淡色高亮或轻量声波反馈，不使用干扰阅读的夸张动画。
- 复习题先显示中文情景和英文挖空句；点击“显示候选”后，候选词从下方自然展开。
- 答对后用柔和的过渡进入下一题；答错不使用红叉、羞辱性文案或奖励特效，而是提供理解与再次学习的路径。
- Windows + Chrome 的基础版需同时支持鼠标和键盘：空格播放当前词/句，`1–4` 选择候选词，`Enter` 进入下一题。所有功能仍须可完全通过鼠标操作。

### 11.4 色彩、字体与动效

- 基础色：暖白、炭黑、极淡蓝灰；避免高饱和霓虹色、厚重渐变和强游戏化色彩。
- 每个故事主题可有一小块低饱和“词境色”作为记忆线索，例如海边的雾蓝、咖啡馆的暖褐、雨天的灰紫；不使用抢眼的大面积背景图。
- 中英文字体都要优先保证长时间阅读的清晰度。英文正文可采用适合阅读的衬线风格，操作文本、音标和中文辅助信息保持干净易读。
- 动效应短、柔和并有明确用途：进入内容、展开释义、播放朗读、显示候选、切换下一题。
- 提供“减少动态效果”开关；高级感来自排版、留白和节奏，不来自炫技。

### 11.5 明确避免的方向

- 儿童化卡通、赛博霓虹、重度玻璃拟态、密集卡片墙；
- 打卡、徽章、排行榜、连续天数刺激等游戏化设计；
- 每篇故事都配置大幅 AI 插画；
- 用复杂动效、数据图表或强烈视觉反馈打断阅读和回忆。

## 19. iPhone 滚动释义卡闪屏修复（2026-08-21 14:35，北京时间）
